## 附和 / 从众问题的研究

- Unanimity Without Persuasion: A Single Round of Debate Erases the Disagreement Signal — https://arxiv.org/html/2609.26145
  7 个异构模型、600 题，一轮讨论后一致率 39.5% → 95.2%，准确率 91.8% → 92.4%，一致地错 8 → 22。建议：在同伴互看之前做验证。
- Talk Isn't Always Cheap: Understanding Failure Modes in Multi-Agent Debate — https://arxiv.org/abs/2509.05396 ，代码 https://github.com/TheNormativityLab/talk-aint-cheap
  讨论会让准确率随时间下降，模型会因同伴推理从对改错。
- The Cost of Consensus: Isolated Self-Correction Prevails Over Unguided Homogeneous Multi-Agent Debate — https://arxiv.org/html/2605.00914
  同质模型无结构辩论基本无用；85.5% 照搬多数；投票丢掉正确答案最多 32.3 个百分点；token 花费是独立自查的 2.1–3.4 倍。
- Voting or Consensus? Decision-Making in Multi-Agent Debate — https://arxiv.org/abs/2502.19130
  推理题投票好 13.2%，知识题共识好 2.8%；成员多更好，讨论轮数多更差；All-Agents Drafting +3.3%，Collective Improvement +7.4%。
- Peacemaker or Troublemaker: How Sycophancy Shapes Multi-Agent Debate — https://arxiv.org/abs/2509.23055
  谄媚会让讨论过早收敛，准确率低于单个模型。
- Minority Sentinel: When to Overturn Majority Voting in Multi-Agent LLM Debates — https://arxiv.org/pdf/2606.29270
  何时该让少数派推翻多数。
- Not All Flips Are Conformity — https://arxiv.org/html/2606.00820 ，代码 https://github.com/47hao030808/Not-All-Flips-Are-Conformity
- Too Polite to Disagree — https://arxiv.org/html/2604.02668 ，代码 https://github.com/mathismusic/multiagent-discussion-sycophancy

### 微信 ClawBot（iLink）协议，照腾讯官方插件源码核对

来源：腾讯官方 npm 包 @tencent-weixin/openclaw-weixin 2.4.9（MIT），源码 dist/src/api/api.js、auth/login-qr.js、cdn/*.js、messaging/send.js、monitor/monitor.js；社区整理 https://github.com/epiral/weixin-bot/blob/main/docs/protocol-spec.md 、https://github.com/x1ah/wechat-ilink-demo

- 地址：https://ilinkai.weixin.qq.com；媒体 CDN：https://novac2c.cdn.weixin.qq.com/c2c。
- 公共请求头：iLink-App-Id（官方插件 package.json 里 ilink_appid = "bot"）、iLink-App-ClientVersion（版本号编成 uint32：major<<16 | minor<<8 | patch）。POST 另加 Content-Type: application/json、AuthorizationType: ilink_bot_token、X-WECHAT-UIN（随机 uint32 转十进制字符串再 base64）、Authorization: Bearer bot_token。每个请求体带 base_info：channel_version、bot_agent（形如 名字/版本）。
- 登录：POST ilink/bot/get_bot_qrcode?bot_type=3（体 {"local_token_list":[]}）→ qrcode、qrcode_img_content（是个链接，编成二维码给微信扫）。GET ilink/bot/get_qrcode_status?qrcode=…（长轮询约 35 秒）→ status：wait / scaned / need_verifycode（要输入微信上显示的数字，带 verify_code 再查）/ expired（刷新二维码，最多 3 次）/ scaned_but_redirect（换 redirect_host 继续查）/ binded_redirect（已绑定过）/ confirmed（bot_token、ilink_bot_id、ilink_user_id、baseurl）。
- 收消息：POST ilink/bot/getupdates {get_updates_buf, base_info}，服务器挂 35 秒；返回 ret、msgs、get_updates_buf（游标，每次存盘）、longpolling_timeout_ms（下次超时）。ret 或 errcode 为 -14 = 会话过期，官方插件暂停 1 小时；连续 3 次失败退避 30 秒，否则 2 秒后重试。
- 消息：from_user_id（…@im.wechat）、context_token（回复时必须原样带回）、create_time_ms、item_list。item type：1 文字 text_item.text；2 图片 image_item（media、aeskey 十六进制）；3 语音 voice_item（text 是微信转好的文字）；4 文件 file_item（media、file_name、len）；5 视频。引用回复在 item.ref_msg（title、message_item）。message_id 是 uint64，要按字符串解析。
- 媒体下载：media.full_url 或 CDN/download?encrypted_query_param=…；AES-128-ECB + PKCS7 解密。密钥：image_item.aeskey（hex）优先，否则 media.aes_key = base64(16 字节) 或 base64(32 位 hex 字符串)。
- 发消息：POST ilink/bot/sendmessage {msg:{from_user_id:"", to_user_id, client_id(唯一), message_type:2, message_state:2, item_list:[一个 item], context_token}}；一条请求只放一个 item，长文按约 2000 字分片、每片新 client_id。
- 发图片 / 文件：POST ilink/bot/getuploadurl {filekey(16 字节 hex), media_type(1 图 2 视频 3 文件), to_user_id, rawsize, rawfilemd5, filesize=ceil((rawsize+1)/16)*16, no_need_thumb:true, aeskey(hex)} → upload_full_url 或 upload_param；把 AES-128-ECB 加密后的内容 POST 到 CDN/upload?encrypted_query_param=…&filekey=…，响应头 x-encrypted-param 就是下载参数。图片 item：{type:2, image_item:{media:{encrypt_query_param, aes_key: base64(hex 字符串), encrypt_type:1}, mid_size: 密文大小}}；文件 item：{type:4, file_item:{media:{…}, file_name, len: 明文大小字符串}}。
- 正在输入：POST ilink/bot/getconfig {ilink_user_id, context_token} → typing_ticket；POST ilink/bot/sendtyping {ilink_user_id, typing_ticket, status: 1 开始 / 2 取消}。

## 做 Word / Excel（2026-10-10，1.5.0）

- 参照产品（第三方文章，官方没细说，未确认）：WorkBuddy 是用户说清输出格式（章节、字体字号、行距、页眉页脚），做好的 Word / Excel / PPT 在「产物」里（https://cloud.tencent.com/developer/article/2638618 、https://www.woshipm.com/share/6438541.html ）；豆包是每条回答可以导出成 Word（https://deepseek.csdn.net/6a422752662f9a54cb85923f.html ）。我们两样都做：成员工具做文件 + 回答下面「存成 Word」。
- 格式依据：ECMA-376（Office Open XML）。Word 的 pPr / rPr / tblPr / tcPr / sectPr / settings 里子元素有固定顺序，错了 Word 会报「文件已损坏」；我们照 schema 顺序写。公文样式参考 GB/T 9704-2012（仿宋三号正文、每行 28 字 22 行左右、一级黑体、二级楷体、页码「— 1 —」）。
- 校验工具：OOXML-Validator 2.1.6（https://github.com/mikeebowen/OOXML-Validator ，MIT，底层是微软 Open XML SDK，win-x64 自带运行时，zip 的 SHA-256 0f22c0da…1acb），解压在 G:\DevCache\tools\ooxml-validator。用法：OOXMLValidatorCLI.exe <文件或文件夹> Office2016 [--all]。
- 微信发文件：官方插件 2.4.9 的 sendFileMessageWeixin——先 getuploadurl（media_type 3 = FILE），AES-128-ECB 加密传 CDN，再发 type 4 的 file_item（media.encrypt_query_param、aes_key = base64(十六进制密钥字符串)、encrypt_type 1、file_name、len = 明文字节数的字符串）。

- 会话：「each conversation is a session: it has its own chat history and project folder, independent of any other session.」每个会话自己的历史、自己的项目文件夹，互不影响。开会话前先在输入区选四样：运行环境（本地、云端、SSH、Windows 上的 WSL）、项目文件夹、模型、权限模式。

- 改动怎么看：改了文件，出现「+12 -1」这样的增删行数标记，点开是差异查看器——左边文件列表、右边每个文件的改动；点任意一行能写评论，攒几条后 Ctrl+Enter 一起交给 Claude，它按评论再改一版新的差异。
- 权限模式有五种：手动（改文件、跑命令前都问，你看着差异逐个接受或拒绝）、接受编辑（自动接受文件编辑和常见文件系统命令，其他终端命令仍问）、计划（只读文件和跑命令来探索，给出计划但不改源码）、自动（不弹常规确认，后台有分类器先检查动作）、绕过权限（完全不问，文档说只该用在沙箱容器或虚拟机里）。访问外部网站时弹卡片：「Allow once」「Always allow」「Deny」。
- 终端：会话标题栏有「Terminal」，也可 Ctrl+`；终端开在会话的工作目录，跟 Claude 共用同一个环境，所以你跑的 npm test、git status 看到的就是 Claude 正在改的文件；只有本地和 SSH 会话有。聊天记录的详细程度有三档：普通、思考、详细（详细会显示每次工具调用、读文件和中间步骤）。
- 预览：Claude 能启动开发服务器并在内置浏览器窗格里验证；开了自动验证会在改完后截图、查错、确认能用再回答。浏览器窗格用独立的干净资料，不碰用户自己的浏览器。
- 本地和云端：本地会话直接在本机访问文件；云端会话在 Anthropic 的机器上跑，关了应用、关了电脑也继续；云端会话可以多仓库；有的功能（@ 文件、文件窗格、插件按钮）云端和 WSL 里没有。
- 手机：本地会话经「Remote Control」连上以后，会出现在其他登录同一账号的设备上（claude.ai/code 和手机 App 的会话列表）；会话里输入 /remote-control 或开关即可；做完或需要你批准时手机收到推送。
- 我们的取舍（草案，没和用户定）：做「会话 = 一个文件夹 + 一段历史」；改动显示差异，能逐条接受或拒绝；先做手动、计划、接受编辑三档，不做「绕过权限」；手机触发走现有加密中转，且手机上必须能看到并批准每一次改动（不做「手机一键放行全部」）。

## Claude Code 接本机 MCP（2026-10-22 查，给「Claude Code 当总指挥」用，设计说明第 18 节）

- Gemini：gemini -p "任务" --output-format stream-json --approval-mode auto_edit --skip-trust。不加 --skip-trust（或环境变量 GEMINI_CLI_TRUST_WORKSPACE=true）时，没信任过的文件夹会退出（退出码 55），提示「not running in a trusted directory」。标准输出一行一个 JSON：init（session_id、model）→ message（role user / assistant，assistant 的 delta=true 是一段段流出来的）→ tool_use（tool_name、tool_id、parameters）→ tool_result（tool_id、status、output）→ result（status、stats：tokens、duration_ms、tool_calls、models）。标准错误有几行 Windows 10 / 真彩色 / 没装 ripgrep 的提示，不是错。
  - 权限：--approval-mode default / auto_edit / yolo / plan（只读）。无界面时要批准的工具不会来问：这次 auto_edit 下它没跑 type 命令，改用 read_file 读了一遍。工具名是它自己的（read_file、replace……），replace 的参数里有 file_path、old_string、new_string，能在事后算出改了哪个文件，但同样拿不到改之前的时机。
  - 续接：-r / --resume latest 或编号。
- 结论：两家都不能逐步问权限、也不能在改文件之前通知我们。接进来要先定「手动档怎么办、撤销靠什么」（当前任务.md 里写了我的方案）。
- 10-20 补测（接进 Code 栏时）：
  - 任务走标准输入：codex exec … -（「-」= 从标准输入读，codex exec --help 原文「If not provided as an argument (or if `-` is used), instructions are read from stdin」）；gemini -p . …（--help 原文「-p, --prompt … Appended to input on stdin (if any).」，实测用户那条 message 的内容是「任务\n\n\n.」）。两家都按要求改了文件。
  - 报错：codex 用不存在的模型时先来一条 item.type=error（「Model metadata for `no-such-model` not found…」，不致命），再来顶层 error 和 turn.failed，error.message 是一整段 JSON 字符串（里面 error.message =「The 'no-such-model' model is not supported when using Codex with a ChatGPT account.」），进程退出码 0。gemini 用不存在的模型：result 的 status=error、error.message=「[API Error: An unknown error occurred.]」，退出码 1。
  - Codex 跑命令有两种写法：「"…\powershell.exe" -Command '…'」和「-Command "…"」（里面的双引号写成 \"）。Gemini 会调一个自己记思路的工具 update_topic（参数 title / summary / strategic_intent）。
  - Codex 的 item 里还有 file_change（这次真跑见到了，路径是完整路径），具体字段我们只用了 changes[].path，别的没细看（未确认）。
